Dev Note: Admin-side organization and role update

Objective

Reorganize the admin-side navigation and management flow to make the system feel simpler, cleaner, and more product-like without breaking any existing working functionality.

This update must only focus on:

1. Moving Reports into Work Log
2. Moving Field Notes into Work Log
3. Renaming Admins to Management
4. Adding role types under Management:

   * Admin
   * Assistant
   * Team

Do not touch attendance logic, schedule logic, payroll calculations, employee hours, cleaner flows, submissions flow, public links, document generation, reports rendering, auth logic outside this scope, or anything else currently working.

Main navigation changes

Current issue
The left sidebar feels too spread out and too administrative. Reports, Work Log, and Field Notes are separated even though they belong to the same operational workflow.

Required change
Simplify the sidebar by making Work Log the parent operational section.

Remove these as standalone sidebar items:

Work Log restructuring

Goal
Work Log should become the central place for all work submission-related actions and views.

Inside Work Log, organize the content using tabs, sub-navigation, segmented controls, or a secondary left panel inside the page. Use the cleanest UI pattern already consistent with the app.

Work Log must include these sections:

1. Submissions / Work Log main list

   * Current work submissions
   * Submitted
   * Reviewed
   * Draft
   * Has review
   * Search and filters remain working

2. Reports

   * This should surface the existing reports view inside Work Log
   * Do not rebuild report logic from scratch
   * Reuse current reports functionality and route/component where possible
   * User should be able to move back and forth easily between submissions and reports

3. Field Notes

   * Move the existing field notes view under Work Log
   * Reuse existing field note logic and rendering
   * User should be able to create, review, and manage field notes from inside Work Log

4. Requests

   * Add a section inside Work Log for requests if requests already exist in the system
   * If requests are already on another page or in an existing module, surface them here through a sub-view, shared component, or embedded route
   * Do not break the existing request functionality
   * This is about simplifying access, not rebuilding the request system

Expected Work Log experience

When a user clicks Work Log, they should land on a unified operational page with clear internal navigation such as:

* Submissions
* Reports
* Field Notes
* Requests

This should feel like one organized workspace instead of several disconnected pages.

Routing recommendation

Do not remove old routes abruptly if they may already be used internally or bookmarked.

Recommended safe approach:

* Keep old routes temporarily as redirects or wrappers
* Route standalone Reports to Work Log > Reports
* Route standalone Field Notes to Work Log > Field Notes
* Route anything referencing old work log route to Work Log > Submissions

This reduces risk and avoids breaking links, saved state, or internal references.

Recommended role permission model

1. Admin
   Purpose
   Full company-level manager for that business.

Access

* Can view dashboard
* Can view and manage employees
* Can view and manage schedule
* Can view and manage attendance
* Can view and manage payroll views if payroll access already exists
* Can view and manage clients
* Can access Management
* Can add another Admin
* Can add Assistant
* Can add Team
* Can access Work Log, Reports, Field Notes, Requests
* Can review submissions
* Can create and manage field notes
* Can contact employees if this exists
* Can view client counts and operational data

Restrictions

* Must not have platform-level super admin powers
* Must not access startup/internal-only controls
* Must not manage system-wide platform settings outside their company scope

2. Assistant
   Purpose
   Support role for office assistance and operational visibility.

Access

* Can view dashboard
* Can view employees
* Can view schedule
* Can view attendance
* Can view payroll
* Can view clients
* Can access Work Log
* Can view reports
* Can view field notes
* Can view requests
* Can follow up operationally

Restrictions

* Cannot add management users
* Cannot edit management roles
* Cannot delete management users
* Cannot create or delete employees unless already intended by business rules
* Cannot change critical settings
* Cannot delete clients
* Cannot change billing, company ownership, or high-risk settings
* Cannot perform destructive actions

3. Team
   Purpose
   Team lead or operational coordinator.

Access

* Can view employees
* Can view schedules
* Can see attendance status
* Can view who clocked in and who did not
* Can access selected Work Log operational views if needed
* Can view clients list summary if needed for coordination
* Can follow up with employees

Restrictions

* Cannot access Management creation or editing
* Cannot add or delete users
* Cannot modify settings
* Cannot change payroll settings
* Cannot perform destructive actions
* Cannot change company-level configurations
* Cannot create or remove admins or assistants

Safe implementation rule
If unsure whether a role should edit something, default to view-only for Assistant and Team.

Permission design guidance

Do not hardcode only front-end hiding.
Implement real permission checks both:

* In the UI
* In the backend/API authorization layer

Why
A hidden button alone is not enough. A user could still hit an endpoint directly.

Minimum safe permission areas to enforce

* Management creation
* Management editing
* Management deletion
* Role assignment
* Settings updates
* Destructive employee/client actions
* Work Log actions that modify records
* Field note creation/edit/delete if restricted
* Report state changes if restricted

UI behavior by role

Admin

* Full Management page visible
* Add Management button visible
* Edit role actions visible as allowed

Assistant

* Management page hidden or view-only depending on product choice
* No Add Management button
* No destructive actions
* View-focused experience

Team

* No Management page access
* Only operational pages needed for team oversight
* View-focused experience

Recommended safe UX

* Admin: full company-management access
* Assistant: broad visibility, limited actions
* Team: operational visibility, minimal change power
