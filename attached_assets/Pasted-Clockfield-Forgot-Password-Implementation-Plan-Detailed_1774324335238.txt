Forgot Password Implementation Plan
Detailed implementation document for business account password recovery using secure email
reset links and Mailgun.

Critical instruction to the agent
Only implement the forgot password and password reset flow for business accounts using secure
email links through Mailgun. Do not delete, refactor, or alter any unrelated feature. Do not touch
attendance, schedule, payroll, employee clock flow, reports, tasks, client links, or any existing
active account logic unless it is directly required for this one feature. If any additional change
seems necessary outside this scope, stop and ask for approval first.
1. Objective
Implement a secure forgot password flow for business accounts so a company user can click Forgot
password, enter the email on file, receive a secure reset link by email, open the link, and set a new
password without affecting any other account or any unrelated module.
This implementation must be isolated from the current login and account system. Existing
authentication must continue to work exactly as it does now for users who are not using the forgot
password flow.
2. Scope and non-scope
In scope:
 Forgot password link on the business login page
 Backend endpoint to request a password reset email
 Secure one-time reset token generation and storage
 Mailgun integration to send the reset email
 Reset password page to accept a new password
 Token validation, token expiry, single-use enforcement, and session revocation for that one user
 Audit logging for reset request and reset completion
Out of scope:
 Any change to employee attendance, schedule, payroll, reports, tasks, client work links, public
reports, reviews, or support flows
 Any rewrite of the current login system
 Any migration of all auth code unless strictly needed for this feature
 Employee self-service forgot password at this stage
 OTP, SMS, or phone-based recovery in this phase
3. Product decision
Business accounts get self-service forgot password by email.
Employee accounts are not part of this first rollout. If an employee needs a password reset, the
business can continue resetting that employee internally using the existing company-side process.
The reset flow must use a secure email link. The email provider for this implementation is Mailgun.
4. Non-negotiable guardrails
 Do not delete any existing table, user, business, employee, attendance, schedule, payroll, report,
task, or review data.
 Do not modify the login success path except to add a Forgot password link and any required
isolated endpoints.
 Do not change password hashing for existing users unless the current method is insecure and the
new method can be applied safely without invalidating current passwords. If a password hashing
migration is required, ask for approval first.
 Do not log out all users globally. Only revoke sessions for the one user who successfully resets their
password.
 Do not expose whether an email exists in the system. The request response must be generic.
 Do not store raw reset tokens in the database.
 Do not send passwords by email.
 Do not let the reset link be reusable.
 If any required dependency or infrastructure change goes beyond this feature, ask for approval
first.
5. End-to-end user flow
1. User opens the business login page.
2. User clicks Forgot password.
3. User enters the email address associated with the business account.
4. Frontend submits the email to the forgot password endpoint.
5. Backend always returns the same generic success response whether the email exists or not.
6. If the email exists and belongs to a business user account, backend creates a one-time reset
token, stores only its hash, sets a short expiry, and sends the email through Mailgun.
7. User receives the email and clicks Reset password.
8. Frontend opens the reset password page with the token from the email link.
9. Frontend calls a token validation endpoint.
10. If valid, user sees the new password form. If invalid or expired, user sees a clean error with an
option to request a fresh link.
11. User enters a new password and submits.
12. Backend validates the token again, validates the new password, updates the password, marks
the token as used, invalidates any other open reset tokens for that same user, and revokes that
user’s sessions only.
13. User can then log in with the new password.

7. Mailgun setup
Mailgun must be configured as a transactional email provider for password recovery.
 Create or use an existing Mailgun account for transactional app email.
 Add a sending domain or subdomain dedicated to the app, for example mail.clockfield.com or
mg.clockfield.com.
 Verify the Mailgun domain in the Mailgun dashboard.
 Publish the DNS records required by Mailgun for SPF and DKIM.
 Enable tracking only if needed. It is not required for password reset to work.
 Use a dedicated sender address such as no-reply@yourdomain.com.
 Store the Mailgun API key in environment variables only. Never hardcode it in frontend or
backend source files.
 Use the correct Mailgun API base URL for the account region.

10. Endpoint behavior details
10.1 POST /api/auth/forgot-password
Input
 { "email": "owner@company.com" }
Behavior
 Normalize the email: trim whitespace and convert to lowercase.
 Apply rate limiting by IP and by email key.
 Always return the same success response whether the account exists or not.
 If the email does not exist, stop after returning the generic response.
 If the email exists but is not a business account eligible for this flow, still return the same generic
response.
 If the email exists and is eligible, create a cryptographically secure random token, hash it, store the
hash with expiry, build the reset URL, and send the email through Mailgun.
Response
 { "message": "If an account exists for that email, we sent a reset link." }
10.2 GET /api/auth/reset-password/validate
 Accept token as query parameter.
 Hash the incoming token using the same hash function used at creation.
 Look up the matching unused token record.
 Reject if not found, already used, or expired.
 Return a simple valid or invalid response that the reset page can use.
10.3 POST /api/auth/reset-password
 Accept token and newPassword.
 Rate limit repeated attempts.
 Hash the token and look up the record again.
 Reject if missing, expired, or already used.
 Validate the password against the current password policy.
 Hash the new password with the same secure password algorithm already used by the app. If the
current app uses bcrypt securely, keep bcrypt for compatibility. If it already uses Argon2, keep
Argon2. Do not change all users’ password hashing method as part of this task.
 Update the user password in a transaction.
 Mark the current token record as used in the same transaction.
 Invalidate any other unused reset tokens for that same user in the same transaction.
 Revoke active sessions for that same user only.
 Write an audit log entry for password reset completed.
11. Security requirements
 Use a cryptographically secure token generator. Recommended raw token length is at least 32
random bytes, encoded as hex or base64url.
 Store only a hash of the token in the database, never the raw token.
 Set a short expiry, preferably 20 minutes. Acceptable range is 15 to 30 minutes.
 Each token must be single-use only.
 Always show the same response on forgot password requests to prevent email enumeration.
 Rate limit the request and reset endpoints to slow abuse.
 Do not include any sensitive account details in the email.
 Do not auto-log the user in after password reset unless that behavior already exists and is
intentionally approved. Safer default is to redirect to login.
 After successful reset, revoke only that user’s sessions so existing active accounts for all other users
remain untouched.
 Add a cleanup job to delete or archive expired and used reset tokens periodically.
12. Mailgun email implementation
Build one dedicated mail service function for password reset. Do not mix forgot password email
sending with unrelated broadcast or marketing email logic.
 Use Mailgun HTTP API with server-side credentials only.
 Read API key and sending domain from environment variables.
 Send both a plain text part and an HTML part.
 Use a subject similar to: Reset your Clockfield password.
 Include exactly one primary CTA button and one fallback URL.
 Do not include login credentials, internal user ID, or debug information in the email.

14. Frontend changes
14.1 Business login page
 Add a Forgot password link below or near the password field.
 Do not redesign or alter the existing login form beyond this one addition.
 Link must go to the new forgot password page.
14.2 Forgot password page
 Single email input field
 Single submit button
 Loading state while request is processing
 Success state that always says the same message
 No message that reveals whether the email exists
14.3 Reset password page
 Read token from URL parameter
 Validate token on page load
 If valid, show new password and confirm password fields
 If invalid or expired, show a clean message and a link back to Forgot password
 On success, show confirmation and route the user back to login
15. Session handling
This feature must not affect unrelated active accounts.
 When a password reset succeeds, revoke sessions for that one business user only.
 Do not revoke sessions for all users in the company.
 Do not revoke sessions for employees unless they share the exact same user account being reset.
 Do not restart or invalidate unrelated auth tokens across the system.

17. Error handling
 If Mailgun is temporarily unavailable, do not break login. Only the forgot password request should
fail gracefully.
 Return a generic success response to the user even if the send fails after internal processing, but
log the provider failure so support can inspect it. If the product team prefers strict delivery
confirmation, ask for approval first.
 If token is expired or invalid, show a clean reset link invalid message and prompt the user to
request a fresh link.
 If password update transaction fails, do not mark the token used unless the password actually
changed.
