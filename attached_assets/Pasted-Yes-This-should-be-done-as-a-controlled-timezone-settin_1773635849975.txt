If the company can type anything they want, the system can end up with:

DEV NOTE

Task
Replace the free-text timezone field in Settings with a proper timezone dropdown selector and make sure the selected timezone is used consistently across the system.

Critical rule
Do not break or affect anything else that is already working.

Do not modify:

auth

login

employee creation

admin creation

client creation

request system

work log

clock in / clock out logic

attendance creation

payroll calculation logic except to ensure it reads the saved timezone correctly

schedule creation logic except to ensure it reads the saved timezone correctly

This task is only about:

replacing the timezone text field with a dropdown

ensuring the selected timezone is valid

ensuring the system uses that saved timezone consistently

Main goal
The company should select a valid timezone from a dropdown, not type arbitrary text.

Why
A typed field like:
America/New_York

is too risky because:

user can type invalid values

user may not know the correct format

one typo can break time calculations

system trust goes down if times are wrong

Required final behavior
In Settings → Company Info:

timezone must be a dropdown

user selects from valid timezone options

system saves the selected valid timezone

all system time displays and date calculations use that saved timezone

System behavior requirement

This is the important part:
The saved timezone must be the system timezone for that company.

That means it should be used wherever “today”, “this week”, “late today”, pay period boundaries, and similar time logic are calculated.

At minimum, timezone must be applied consistently to:

dashboard metrics

attendance daily filters

late today counts

missed shift counts

schedule display

work date display

payroll period date boundaries

request timestamps if they are company-facing

cleaner hours date ranges

Do not let one page use browser local time and another page use server UTC if the company timezone is set.

Source of truth rule
The company timezone setting must become the main timezone source for that company.

Do not keep using freeform fallback strings after the dropdown is added.

Validation rules

Backend

accept only valid timezone values from allowed list or valid IANA values if using full support

reject invalid strings

do not save malformed values

Frontend

dropdown only allows valid selection

no manual typing unless using searchable controlled select with valid options only

Migration / backward compatibility

Important because app is live.

If existing companies already have a timezone text value saved:

preserve valid existing values

if saved value matches a valid timezone, preselect it in the new dropdown

if saved value is invalid or empty, default carefully
