Dev note for agent

Task
Fix only the report branding logo persistence issue in Clockfield admin settings.

Problem
The company logo upload works at first, but after some time the saved logo stops showing consistently. The admin uploads it, saves it, and it may appear for a while, then disappear or fail to display even though it was already saved.

Scope
Only fix the logo persistence and display issue for Report Branding.
Do not change:

payroll
deductions
branding color
default service summary
report layout
auth
storage structure unless strictly required for this fix
any other settings logic
any working public report flow
If anything outside this exact issue needs to be changed, stop and ask for approval first.

Expected result
Once an admin uploads and saves a company logo:

it must remain saved
it must still show after refresh
it must still show after logout and login
it must still show after several minutes or hours
it must still show on the public report header
it must not randomly disappear
replace logo and remove logo must continue to work properly

Likely root causes to check
Check these first before changing code broadly.

Logo URL is only being held in local state
Possible issue:
file uploads successfully
preview uses temporary frontend state or object URL
permanent saved URL is not reliably being read back from database
Temporary signed URL is expiring
Possible issue:
stored value may be a signed URL or temporary access URL
once it expires, the image breaks
Correct behavior:
database should store a stable object key or permanent public URL
frontend should request a fresh display URL if needed, instead of storing expiring URLs as the source of truth
Save flow uploads file but does not persist final path correctly
Possible issue:
upload finishes
settings save succeeds visually
actual database field is empty, stale, or overwritten on later settings save
Settings read endpoint is returning stale or null logo field
Possible issue:
backend save is correct
frontend fetch later returns old cached settings or wrong field mapping
Browser caching issue
Possible issue:
replace logo uses same URL/path
browser caches broken or old asset
Need:
versioning or cache busting on replace only
do not use random cache busters on every render unless needed
Storage cleanup or overwrite issue
Possible issue:
old upload is deleted too early
replace flow writes new file but frontend still points at removed asset
file path collision creates inconsistent result

Required fix strategy
Use a stable, predictable logo persistence flow.

Recommended implementation

Treat logo storage in two layers
Layer A: persistent database value
Save only a stable logo reference in company/business settings
Prefer one of these:
logoStorageKey
logoPath
logoFileName plus known base path
permanent public logoUrl if your storage is public and stable

Do not store:

blob URL
object URL
short-lived signed URL as the permanent saved value

Layer B: display URL

When rendering the image, derive the actual display URL from the saved persistent reference
If the storage system requires signed URLs, generate a fresh signed URL at read time
If the bucket is public, construct the public URL from the stored path
Fix the save flow
When admin clicks Replace Logo and then Save Settings:
upload file first
confirm upload success
receive stable storage key/path/public URL
save that stable value into company/report branding settings in database
return saved settings payload from backend
frontend should update state using the backend returned value, not the temporary upload preview
Fix the settings load flow
When settings page opens or refreshes:
fetch company settings from backend
load stored logo reference
resolve it into a valid display URL
render the logo preview from saved data, not from previous local state
Fix the public report header flow
When public report renders:
use the saved company logo reference from the source of truth
resolve it the same way every time
do not depend on leftover session state or frontend memory
Handle replace logo correctly
When replacing an existing logo:
upload new logo
save new stable reference
only after successful save, optionally clean up old file if your storage system supports that safely
never delete the old file before the new value is confirmed saved
if cleanup is risky, leave old file in place for now and ask later before optimizing storage
Handle remove logo correctly
When clicking Remove logo:
clear the stored database field
remove preview immediately in UI after successful backend response
public report should then show no logo gracefully
do not break brand color or header layout

Backend

Frontend

Check whether the current preview uses URL.createObjectURL or similar
If yes, use that only for temporary preview before save, never as permanent saved state
After successful save, replace temporary preview with the persisted backend value
On page reload, render only from fetched saved settings

Database

Verify the logo field is not being reset by unrelated settings updates
Verify Save Settings does not overwrite logo with null when no new file is selected
This is very important.
If admin changes brand color or summary text without uploading a new logo, the existing saved logo must remain untouched.

Critical rule for update payloads
Do not accidentally null out the saved logo when saving other branding fields.
Common bug:

frontend sends logo: null if no new file is selected
backend overwrites existing saved logo with null
Fix:
only update logo field when:
a new upload succeeded, or
user explicitly clicked remove logo

Recommended safe logic
Case 1: new logo uploaded

save new stable logo reference

Case 2: no new logo uploaded

keep existing saved logo reference unchanged

Case 3: remove logo clicked

clear saved logo reference

Cache handling
If the same file path is reused on replace, the browser may show stale results.
Safer options:

generate unique file names for each uploaded logo
Example:
company-<companyId>-logo-<timestamp>.png
then save the new file path
This avoids browser cache conflicts and is the safest fix.

If you must keep the same path, add versioning:

save updatedAt or logoVersion
append it as a query param only for display
But unique filenames are cleaner and safer.

Validation

Recommended:
max file size limit if already present
do not add new UI behavior unless needed

Suggested implementation summary
The safest fix is:

store a stable logo file key/path in the database
never store a temporary preview URL as the saved value
on settings load and public report render, always resolve from that saved stable value
preserve existing logo when saving other fields unless remove was explicitly chosen
use unique filenames for replaced logos to avoid cache issues
