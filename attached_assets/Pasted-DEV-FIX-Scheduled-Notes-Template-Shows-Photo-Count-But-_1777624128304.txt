DEV FIX: Scheduled Notes Template Shows Photo Count But Opens Empty

Project: Clockfield
Area: Work Log → Scheduled Notes → Templates
Issue: Template card shows photo tasks, but template detail page shows 0 photo tasks and no uploaded images.

Do not break or affect anything currently working.

Do not touch regular Field Notes.

Do not touch normal Work Log.

Do not touch clock-in/out, attendance, payroll, clients, auth, Stripe, reports, or unrelated pages.

Only fix Scheduled Notes template detail loading and display.

Problem

On the template list page, the card shows:

daily
1 main step
7 photo tasks

That means the system knows the template has data.

But when opening the template, the detail page shows:

daily
1 main step
0 photo tasks

Inside the main step:

Women’s Washroom
0 photo tasks

No uploaded images show.

This means the creation flow is saving the photo tasks or counting them somewhere, but the template detail page is not loading or mapping those photo tasks correctly.

Most likely causes:

The template list endpoint includes photo task count.

The template detail endpoint only returns main steps, but not nested photo tasks.

The frontend detail page expects a different field name than the backend returns.

The uploaded reference images are saved, but not attached to the main step response.

The query cache is stale after saving the main step.

The main step exists, but its photoTasks array is empty on the detail page.

Correct main step count

Correct photo task count

Each main step

All uploaded photo tasks inside that main step

1. Check Template Detail API Response

Find the endpoint used when opening one Scheduled Notes template.

Likely route examples:

GET /api/scheduled-notes/templates/:id
GET /api/scheduled-field-notes/templates/:id
GET /api/worklog/scheduled-notes/templates/:id

Make sure this endpoint returns nested data like:

{
  id: string;
  name: string;
  templateType: "commercial" | "residential";
  status: "active" | "inactive";
  mainSteps: [
    {
      id: string;
      title: string;
      mainArea: string;
      specificArea: string;
      instruction?: string;
      sortOrder: number;
      photoTasks: [
        {
          id: string;
          title: string;
          itemName: string;
          referenceImageUrl: string;
          sortOrder: number;
          isRequired: boolean;
        }
      ]
    }
  ]
}

If the endpoint only returns this:

{
  id: string;
  name: string;
  mainSteps: [
    {
      id: string;
      title: string;
      photoTasksCount: 7
    }
  ]
}

That is not enough.

Fix it to include the actual photo task records.

2. Backend Must Include Photo Tasks

Update the backend query for the single template detail endpoint.

Use the existing ORM style in the app.

Concept:

const template = await db.scheduledNoteTemplate.findFirst({
  where: {
    id: templateId,
    companyId: currentUser.companyId,
  },
  include: {
    mainSteps: {
      orderBy: { sortOrder: "asc" },
      include: {
        photoTasks: {
          orderBy: { sortOrder: "asc" },
        },
      },
    },
  },
});

If using Drizzle or raw SQL, join:

scheduled_note_templates

scheduled_note_main_steps

scheduled_note_photo_tasks

Then group the result into:

template.mainSteps[].photoTasks[]

Important:

Do not create new tables if data is already being saved.

Do not rename tables unless absolutely required.

Just make sure the detail endpoint returns the same saved photo tasks that the list count is using.

3. Check Field Name Mismatch

The frontend may expect:

mainStep.photoTasks

But backend may return:

mainStep.tasks
mainStep.steps
mainStep.subSteps
mainStep.photos
mainStep.photo_tasks

Fix by normalizing the response in one place.

Frontend safe mapper example:

const normalizedMainSteps = (template?.mainSteps || template?.sections || []).map((step: any) => ({
  ...step,
  photoTasks:
    step.photoTasks ||
    step.tasks ||
    step.steps ||
    step.subSteps ||
    step.photos ||
    [],
}));

Preferred fix:

Make backend return one consistent field:

photoTasks

Then update frontend to read:

mainStep.photoTasks

Do not keep multiple random field names long term.

4. Fix Template Header Count

The template detail header should not say 0 photo tasks when photo tasks exist.

Calculate from nested photo tasks:

const mainStepCount = template?.mainSteps?.length || 0;

const photoTaskCount =
  template?.mainSteps?.reduce((total, mainStep) => {
    return total + (mainStep.photoTasks?.length || 0);
  }, 0) || 0;

Use this for the header:

{mainStepCount} main step{mainStepCount === 1 ? "" : "s"} · {photoTaskCount} photo task{photoTaskCount === 1 ? "" : "s"}

Also use the same count inside each main step:

{mainStep.photoTasks?.length || 0} photo tasks
5. Fix Save Main Step Flow

When the admin creates a main step with multiple images:

The save action must create:

1 main step record

7 photo task records if 7 images were uploaded

Each photo task must have:

mainStepId

templateId

title

itemName if available

referenceImageUrl

sortOrder

isRequired

createdAt

If only the main step is created but the photo task creation fails, show an error and do not pretend the template has saved correctly.

Use a transaction if possible.

Concept:

await db.transaction(async (tx) => {
  const mainStep = await tx.createMainStep(...);

  for (const [index, photo] of uploadedPhotos.entries()) {
    await tx.createPhotoTask({
      templateId,
      mainStepId: mainStep.id,
      title: generatedTitles[index],
      itemName: selectedItems[index] || `Photo ${index + 1}`,
      referenceImageUrl: photo.url,
      sortOrder: index,
      isRequired: true,
    });
  }
});

After save succeeds, invalidate/refetch:

queryClient.invalidateQueries({ queryKey: ["scheduled-note-template", templateId] });
queryClient.invalidateQueries({ queryKey: ["scheduled-note-templates"] });

This prevents stale UI where the list count updates but the detail page stays empty.
