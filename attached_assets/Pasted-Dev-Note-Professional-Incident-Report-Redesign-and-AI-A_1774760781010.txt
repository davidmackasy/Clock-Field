Dev Note: Professional Incident Report Redesign and AI-Assisted Incident Writing for Clockfield

Objective

Redesign the Incident Report experience so it looks professional, client-ready, branded per company, easier to fill out, and smarter to generate.

This is not just a visual cleanup.
This is a product-quality incident reporting upgrade.

The current exported report is not professional enough for client-facing use because it exposes internal wording like “admin,” shows “submitted” status, shows internal-style metadata too prominently, and includes an unprofessional footer link. The uploaded reference text also points to the core pieces incident reports should include: date/time/location, clear factual description, witnesses, action taken, and prevention recommendations.

Critical instruction

Do not touch or break anything else.

Do not refactor unrelated pages.
Do not change unrelated report flows.
Do not alter current auth, billing, tasks, submissions, client reports, payroll, notifications, logo storage, or settings logic unless directly required for this exact feature.
Do not change anything outside the incident report experience unless approval is given first.

If any extra change outside this scope is needed, stop and ask for approval first.

Main goals

Make the incident report export and print layout look like a real business document
Remove internal wording that looks unprofessional to clients
Pull the correct company branding automatically from that company’s saved settings
Add guided autofill inputs and dropdowns so incident reports are faster to create
Add AI refinement so poor raw descriptions can be rewritten into a professional factual incident summary before final generation
Keep internal-only fields visible only inside the platform, not in client-facing PDF/export
Preserve multi-tenant behavior so every company gets its own logo and company details

What is wrong in the current sample

From the sample shown:

“Status: SUBMITTED” should not appear prominently on a client-facing exported document
“Prepared By (Admin)” is internal wording and should never be shown in a document that goes to a client
“Employee Acknowledgement” and “Client Acknowledgement” are okay as concepts, but the labels need to be cleaner and more formal
The footer showing a raw Replit URL is not professional and must be removed from the exported PDF
The document needs better structure, better naming, and stronger separation between internal workflow fields and external/client-facing fields
The correct company logo is missing or not being rendered reliably
The report content needs better autofill helpers and better writing quality

Reference guidance from the uploaded text

The uploaded reference text is useful for the structure of a good work incident report. It highlights that a strong report should include accurate event details, a factual description, names of affected parties and witnesses, incident causes, action taken, and follow-up recommendations. It also stresses clear step-by-step explanation and proofreading before submission.

Product decision

Separate platform workflow language from client-facing document language.

Inside Clockfield:
it is okay to use internal workflow terms like draft, submitted, in review, awaiting signature, internal notes, admin review.

In exported PDF / print document:
use professional business wording only.

Examples:

“Prepared by admin” → replace with “Prepared by” or “Prepared by Company Representative”
“Admin Review” → replace with “Management Review” or “Office Use Only”
“Submitted” → do not show on client-facing PDF header unless there is a business reason; if needed, use small “Document Date” or “Prepared Date” instead
internal IDs should be secondary and subtle, not dominant

AI-assisted writing requirement

Add AI refinement for incident text using OpenAI.

The purpose is not to fabricate facts.
The purpose is to rewrite rough user input into a cleaner, factual, professional incident description.

OpenAI’s platform supports structured outputs and JSON-schema-constrained responses, which is useful here because the app can ask the model to return specific fields like refined title, factual summary, likely causes, immediate action, and follow-up recommendations in a predictable format.

AI behavior requirements

The AI must:

preserve the facts the user provided
improve grammar and clarity
remove emotional or blame-heavy language
rewrite into factual business tone
suggest a professional incident title
suggest a concise sequence-of-events paragraph
suggest possible follow-up recommendations
never invent injuries, damages, witnesses, or admissions the user did not provide
ask for more detail in the UI if the input is too weak instead of hallucinating

Recommended AI outputs

When the user enters rough notes, the AI should generate:

Incident title
Refined incident description
Contributing factors or probable cause wording
Immediate action taken summary
Follow-up recommendation text
Optional shorter client-facing summary
Optional internal management summary

Suggested UX:
Button label:
Refine with AI

Flow:

user types rough incident notes
user clicks Refine with AI
model returns polished structured text
user can review and edit before saving
nothing is auto-finalized without user review

Important:
AI must be assistive, not automatic final authority.

Suggested OpenAI integration pattern

Use a server-side OpenAI call only.
Do not expose API keys on the client.
Use structured output with a strict JSON response shape so the returned content maps safely into the incident report sections. The OpenAI API documentation explicitly supports schema-based structured outputs for this kind of constrained generation.

Suggested response schema shape

title
refined_description
sequence_of_events
immediate_action
probable_causes
follow_up_recommendations
confidence_or_missing_details_note

If the raw input is weak, the model should return something like:
“More detail needed about location, item affected, and immediate action.”

Do not generate fake specifics.
