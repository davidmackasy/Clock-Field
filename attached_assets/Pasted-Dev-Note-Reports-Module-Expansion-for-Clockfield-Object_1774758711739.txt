Dev Note: Reports Module Expansion for Clockfield

Objective

Build a new Reports system that allows structured reporting and document sharing between admin, cleaners/employees, and clients inside Clockfield.

This feature must support more than only incident reports. It must become one central Reports page where users can create, receive, review, sign, download, print, and track different report types depending on their role and permissions.

This implementation must be done carefully without breaking or affecting any currently working feature, flow, UI, database relation, request system, authentication, notifications, reports, payroll, tasks, clock-in/out, or client portal behavior.

Critical instruction

Do not touch, refactor, rename, remove, or alter any existing working logic unless it is directly required for this feature.

Do not replace any existing current request flow yet unless explicitly approved.

Do not change anything outside the scope of this dev note.

If any change outside this scope becomes necessary, stop and ask for approval first.

Main product goal

Create one premium Reports page that works as a professional reporting hub.

This page should support:

Admin receiving reports from cleaners/employees
Admin receiving reports from clients
Admin sending reports to cleaners/employees
Admin sending reports to clients
Cleaner/employee sending reports only to admin
Client sending reports only to admin
Cleaner/employee must not be able to send incident reports directly to clients
Client must not be able to send reports directly to cleaners/employees
Admin controls and manages the report workflow between all sides

This means admin acts as the control center for report routing.

High-level product decision

Do not destroy or hard-replace the existing Requests page logic immediately.

Safer rollout:

Phase 1
Create a new Reports module/page and connect it cleanly.

Phase 2
Allow existing request-style issue submissions to also appear under Reports if needed through shared backend mapping or mirrored records.

Phase 3
Only after stable testing, decide whether Requests should later be renamed, merged, or redirected into Reports.

This protects the current working app.

Core concept

The new Reports page should not only be a single report form.

It should act like a reporting center with different report/document actions depending on the user role.

Incident Report purpose

This is used when something serious or important happened at a site or during service.

Examples:

employee broke equipment or property
flooding or water overflow
damaged tap or fixture
item was removed from site without proper reporting
property damage
safety concern
missing item
customer complaint tied to an event
accidental misuse of supplies/equipment
near miss or risky event

Important business logic

Incident reports must remain factual, structured, reusable, and professional.

Do not design them as free-text emotional messages.

Structure must be mostly fillable fields plus short description areas.

Company branding requirement

Every company in Clockfield is separate.

The report must automatically pull company branding and company profile details from that company’s settings.

The generated incident report and other official report documents must show:

company logo
company name
company email if available
company phone if available
company address if available
company contact/admin name if available

If a company has uploaded a logo in settings, that exact saved logo must appear on the report.

Do not hardcode a single global Clockfield logo for company reports.

This must be tenant-safe and company-specific.

Client/site linking requirement

When creating a report, admin must be able to select:

client
site/location
employee/cleaner involved
report type
date/time of incident or event

The selected client should appear on the final report.

The selected location/site should appear on the final report.

The selected cleaner/employee should appear on the final report where applicable.

Example flows

Flow A: Cleaner reports issue to admin

Cleaner opens Reports
Selects Issue Report or Incident Report
Fills fields
Uploads photos
Submits to admin
Admin receives under Incoming Reports
Admin reviews
Admin may convert it into formal incident report
Admin sends formal report to employee and/or client if needed

Flow B: Client reports problem to admin

Client opens Reports
Selects Issue Report or Complaint Report
Uploads photos and description
Sends to admin
Admin receives and reviews
Admin may escalate into incident/damage report
Admin may send official report back to client and relevant cleaner

Flow C: Admin creates incident report and sends to employee

Admin clicks Create Report
Chooses Incident Report
Selects client, site, cleaner
Fills structured fields
Adds evidence
Saves draft or sends
Employee receives under My Reports
Employee adds statement and signs
Admin finalizes
PDF can be downloaded or printed

Flow D: Admin sends incident report to client

Admin creates report
Selects client and incident details
Requests client acknowledgement
Client receives report
Client reviews and signs or comments
Admin finalizes

Flow E: Admin handles both client and cleaner for same report

Admin creates one report record
Admin assigns employee and client to same report
Each side sees only allowed sections
Employee fills employee statement section
Client fills acknowledgement section
Admin sees all sections and finalizes

Routing and transaction rules

Implement strict report routing rules.

Allowed:

admin -> cleaner
admin -> client
admin -> internal admin
cleaner -> admin
client -> admin

Not allowed:

cleaner -> client
client -> cleaner
cleaner -> client through incident report
client -> cleaner through issue report

Any attempt outside allowed flow should be blocked by role-based backend validation, not only frontend UI hiding.

Do not rely only on frontend visibility.
